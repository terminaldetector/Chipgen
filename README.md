**chipgen: композиция напрямую в честный YM2612**

Раньше AI-музыка на чипе — это промпт в текстовое поле и надежда, что чёрный ящик правильно интерпретирует «Sega Genesis, hardcore, dark minor key». Здесь можно писать ноты напрямую: канал, инструмент, нота, длительность — и это идёт не в имитацию звука чипа, а в настоящую эмуляцию YM2612 (ядро Nuked-OPN2, реверс-инжиниринг по фото кристалла) и Sega PSG, реализованного с нуля по регистровой спецификации, вплоть до 16-битного LFSR шума.

Приложенный трек сочинён этим способом руками, не сгенерирован: D minor, i-VI-III-VII (Dm-Bb-F-C). Лид молчит первый такт, задаёт вопрос во втором, отвечает ниже в третьем, поднимается к пику перед возвратом в тонику в четвёртом. PSG-арпеджио меняется вместе с гармонией, не залипает на одной форме.

Движок — плагинная архитектура: облачная модель и локальная сеть как два бэкенда в одном реестре, рендер не знает и не спрашивает, откуда пришли ноты. DefleMask для нейросетей — только теперь ещё и для рук.

# chipgen — DefleMask для нейросетей

Генеративный chiptune-движок поверх настоящей эмуляции YM2612 (FM, Sega
Genesis/Mega Drive) и SN76489 (Sega PSG). Не синтезирует "под чиптюн" —
управляет теми же регистрами, что и настоящий чип, через тот же
протокол записи, с теми же таймингами. Любая нейросеть (или
rule-based/генетический алгоритм — архитектура не важна) управляет этим
через плоский поток событий, не через сырые параметры FM-операторов.

## Архитектура

```
core/ym3438.c + wrapper.c   -> libopn2.so   (Nuked-OPN2, cycle-accurate YM2612)
core/psg.c                  -> libpsg.so    (Sega PSG, register-level модель)
python/opn2.py               ctypes-биндинг + нотный API поверх YM2612
python/sn76489.py            ctypes-биндинг + нотный API поверх PSG
python/instruments.py        банк FM-патчей (bass, distorted_lead, bell_pluck, jazz_chord_pad)
python/events.py             СЛОВАРЬ СОБЫТИЙ — интерфейс для генеративной модели
python/sequencer.py          события -> рендер обоих чипов -> ресемплинг -> микс
python/demo_generator.py     rule-based ЗАГЛУШКА вместо нейросети (доказывает что всё работает)
examples/render_demo.py      полный прогон, пишет output/demo.wav
```

## Быстрый старт

```bash
cd python
python3 ../examples/render_demo.py
# -> output/demo.wav, ~5.7 сек, 44100 Hz, стерео
```

Готовый демо-рендер уже приложен (`output/demo.wav`) — можно послушать
без запуска ничего.

## Точка подключения нейросети

Всё, что нужно модели — вернуть `List[Event]` из `events.py`:

```python
from events import Wait, FMInstrumentSelect, FMNoteOn, FMNoteOff, End

events = [
    FMInstrumentSelect(channel=0, instrument="bass"),
    FMNoteOn(channel=0, note="A", octave=2),
    Wait(ticks=24),
    FMNoteOff(channel=0),
    End(),
]

from sequencer import Sequencer
audio = Sequencer().render(events)   # numpy float32, shape (N, 2), [-1, 1]
```

Это и есть контракт: модель (transformer/RNN/RL-агент/генетика — что
угодно) генерирует токены из этого словаря, `Sequencer` превращает их в
звук через настоящую эмуляцию чипов. `demo_generator.py:generate_pattern()`
— единственное место, которое нужно заменить на `model.generate(...)`;
ничего ниже по цепочке трогать не надо. Каждый `Event` — это
`@dataclass` с `.to_dict()`/`Event.from_dict()`, так что словарь легко
сериализуется в JSON или токенизируется под конкретную архитектуру
(one-hot по типу события + числовые поля, или текстовый JSON-per-line
для LLM-подхода).

Инструменты в `instruments.py` — то же самое разделение труда, что в
DefleMask: паттерн ссылается на инструмент по имени, вся физика
FM-оператора (алгоритм, feedback, ADSR каждого из 4 операторов) живёт
отдельно в банке. Можно дописать свои инструменты как `FMInstrument`
из `opn2.py`, не трогая остальной код.

## Технические заметки о точности

- **YM2612**: ядро — [Nuked-OPN2](https://github.com/nukeykt/Nuked-OPN2)
  (nukeykt), реверс-инжиниринг по фото кристалла YM3438, cycle-accurate.
  Не переписывал синтез с нуля намеренно — это единственный по-настоящему
  надёжный способ дать "макс. достоверный" звук чипа, о котором шла речь
  весь разговор.
- **Busy-флаг**: в процессе тестов всплыла ошибка — без паузы между
  записью адреса и данных чип отбрасывает часть регистровых записей
  (реальное поведение железа, не баг эмулятора). Нашёл нужную задержку
  прямо в исходнике (`write_busy_cnt` тайминг), `opn2_write()` теперь
  всегда доклацывает ~40 внутренних тактов после записи — можно не
  думать об этом на уровне Python.
- **Нативная частота YM2612** ≈ 53267.04 Гц (NTSC), выведена из
  документированного отношения "1 вызов Clock = 6 тактов чипа" и
  24-slot FM-конвейера (6 каналов × 4 оператора). Рендерится на этой
  частоте, затем ресемплится в 44100.
- **SN76489**: написан с нуля по спецификации SMS Power! — 16-битный
  LFSR (не 15-битный, как в оригинальном TI-чипе — Sega-версия шире),
  фидбэк на битах 0 и 3 для white noise, сброс на 0x8000, полная
  register-level модель счётчиков, а не готовая формула частоты.
  Нативная частота ≈ 223721.56 Гц (clock/16).
- Обе частоты — реальные для NTSC Genesis (`master clock / 7` для
  YM2612, впаянный "3.58 MHz" для PSG). PAL-константы тоже есть в коде
  (`PAL_CHIP_CLOCK`/`PAL_PSG_CLOCK`), на случай если нужен PAL-питч.

## Облачные модели — тоже работает

Контракт — `List[Event]`, и Sequencer не знает и не спрашивает, откуда
он взялся. Локальная сеть в том же процессе, RL-агент, генетика или
синхронный вызов облачного API — без разницы, лишь бы на выходе был
этот список (или JSON, который в него конвертится).

`python/cloud_generator.py` — рабочий пример на Anthropic API: промпт
целиком описывает словарь событий и банк инструментов, модель обязана
вернуть только JSON-массив, дальше — устойчивый парсинг (переживает
markdown-обёртку вокруг JSON, забытый `End`) и валидация каждого
события через `Event.from_dict`. Смена провайдера — это правка одной
функции `_call_model()`, всё остальное в файле не трогается.

```bash
pip install anthropic --break-system-packages
export ANTHROPIC_API_KEY=...
cd python && python3 cloud_generator.py   # -> ../output/cloud_demo.wav
```

Без ключа скрипт не падает — показывает офлайн-путь на моковом ответе,
чтобы было видно, что парсинг/валидация работают сами по себе.

Единственная реальная оговорка: это по-прежнему batch-архитектура —
сначала весь список событий, потом рендер. Для облачной модели,
которая один раз выдаёт целый паттерн, это ровно то, что нужно. Если
захочется живой пошаговой генерации нота-за-нотой в реальном времени —
вот там сетевая задержка облака (сотни мс на запрос) уже станет
проблемой; для этого нужна локальная модель в том же процессе, не
облако.

## Плагинная архитектура: облако и локальное — одинаково first-class

`python/generators/` — тот самый "плагин" слой. Общий контракт:

```python
class Generator(ABC):
    def generate(self, style, bars, bpm, ticks_per_second=192.0, **kw) -> List[Event]: ...
```

Три бэкенда уже зарегистрированы под именами, ничего не хардкожено:

```python
from generators import get_generator, available
print(available())  # ['cloud:anthropic', 'local:model', 'local:rule_based']

audio = Sequencer().render(get_generator("local:rule_based").generate("", bars=4, bpm=172))
```

- `local:rule_based` — детерминированная заглушка (`demo_generator.py`), не требует ни сети, ни модели, полезна как smoke-test
- `cloud:anthropic` — синхронный вызов облачного API (`cloud_generator.py`)
- `local:model` — честно НЕ заряжен: `generators/local_model.py` бросает понятную ошибку вместо того чтобы притворяться рабочим. Это розетка под настоящую локальную сеть (PyTorch/ONNX/GGUF — что угодно), а не готовое решение; своего обученного чекпоинта под словарь событий в проекте нет.

Новый бэкенд — это `register("cloud:openai", MyGenerator)`, ничего в
`sequencer.py` или вызывающем коде трогать не надо. Именно то
разделение, о котором была речь: облачное и локальное — два плагина в
одном реестре, а не два разных способа собирать проект.

## examples/claude_composition.py — сочинил лично, не алгоритм

Не генератор, не подключение к модели — обычная композиторская работа,


## Чего пока нет

- DAC/PCM-канал YM2612 (сэмплы, как в Contra: Hard Corps под барабаны) —
  видно как `dacen`/`dacdata` в структуре чипа, но не подключено к
  Python-слою
- LFO и SSG-EG у YM2612 не выведены в высокоуровневый API (регистры
  доступны через `ym.write()` напрямую, если нужно)
- PSG DC-offset трюк для сэмплов (см. README Nuked-OPN2 /SMS Power про
  "playing samples on the PSG") не обёрнут отдельным методом
- Стерео-панорамирование по каналам сейчас фиксировано на "оба канала
  в центр" — `set_instrument` жёстко пишет `0xC0` в панораму, но
  регистр 0xB4+ch открыт для прямой записи
