# chipgen — DefleMask для нейросетей

Генеративный chiptune-движок поверх настоящей эмуляции YM2612 (FM, Sega
Genesis/Mega Drive) и SN76489 (Sega PSG). Не синтезирует «под чиптюн» —
управляет теми же регистрами, что и настоящий чип, через тот же протокол
записи, с теми же таймингами. Любая нейросеть (или rule-based/генетический
алгоритм — архитектура не важна) управляет этим через плоский поток
событий, не через сырые параметры FM-операторов.

Два способа этим пользоваться, и оба first-class:

1. **Как плагин.** Регистрируешь бэкенд в реестре генераторов и гоняешь
   в длинноживущем процессе — облако, локальная сеть, что угодно.
2. **Как ZIP-мост.** Кидаешь архив в ChatGPT/Claude с песочницей, пишешь
   одну строку промпта — и получаешь готовый трек. Ничего не
   разворачивается, ничего не устанавливается. См. [«Мост»](#мост-кинул-zip--получил-трек).

Промпт, который ставится системным при обоих способах — `bridge/CORE.md`.
Это не описание API, а сам чип: полтора десятка мест, где YM2612
противоречит общим знаниям об FM-синтезе, каждое с замером. Все они
ломаются молча — рендер проходит, звук неправильный. Готовый запрос на
демо — в `bridge/PROMPT.md`.

## Быстрый старт

```bash
python3 bridge/bootstrap.py          # соберёт ядра чипов и проверит себя
python3 python/chipgen.py --demo     # -> output/chipgen_demo.wav + .vgm
python3 tests/run_tests.py           # 60 тестов, без единой зависимости
```

`bootstrap.py` находит компилятор и собирает C-ядра; если компилятора нет
— переключается на pure-Python ядра из `python/fallback/`. numpy и scipy
используются если стоят и не нужны если нет. Сеть не нужна вообще.

## Три способа написать музыку

**Трекерная нотация** — компактно, читаемо, дёшево по токенам:

```
bpm 168
lpb 4
inst fm0 bass
inst fm1 square_lead
cols fm0 fm1 psg0 noise dac

D-2  ...  D-5    ...  kick
...  A-4  A-5:6  w1   hat
A-2  ...  F-5    ...  snare
...  ===  ===    ===  hat
```

```bash
python3 python/chipgen.py song.trk -o song.wav --vgm song.vgm
```

**JSON-события** — если модели удобнее structured output:

```json
[{"type": "FMInstrumentSelect", "channel": 0, "instrument": "bass"},
 {"type": "FMNoteOn", "channel": 0, "note": "A", "octave": 2},
 {"type": "Wait", "ticks": 24},
 {"type": "FMNoteOff", "channel": 0},
 {"type": "End"}]
```

**Python напрямую** — когда пишешь код, а не партитуру:

```python
import sys; sys.path.insert(0, "python")
import chipgen

result = chipgen.compose(open("song.trk").read(), wav="song.wav", vgm="song.vgm")
print(result.summary())     # 82 events, 1.42s, peak 0.927, song.wav, song.vgm
```

Все три идут через один и тот же `List[Event]` и один и тот же рендер.

## Что получается на выходе

| файл | что это |
|---|---|
| `.wav` | 16-бит PCM, играет везде |
| `.vgm` | **лог регистров.** Играет в любом VGM-плеере, **импортируется в DefleMask и Furnace**, весит килобайты вместо мегабайт |
| `.vgz` | то же, гзипнутое (плееры это едят) |
| `.trk` | сама партитура текстом — читается и диффается |

VGM тут не второй рендерер, а тот же прогон, записанный с другой стороны:
писатель подключён логгером к тем же объектам чипов, которые рендерят
звук, поэтому байты в файле — это буквально байты, ушедшие в эмулятор.
Разойтись они не могут по построению. `python/vgm_player.py` играет VGM
обратно — чем тесты и пользуются, чтобы проверить, что экспорт не врёт
(и заодно это значит, что чужие Genesis-VGM тоже рендерятся).

## Мост: кинул ZIP — получил трек

Идея простая: плагин надо куда-то разворачивать, а ZIP можно просто
приложить к сообщению. Модель с песочницей распаковывает архив, читает
`START_HERE.md`, запускает `bridge/bootstrap.py` — и композитор готов.
Тот же движок, тот же звук, ноль инфраструктуры.

```bash
python3 bridge/make_zip.py           # -> dist/chipgen-bridge.zip, ~115 КБ
```

Дальше — приложить архив и написать (полные варианты в `bridge/PROMPT.md`):

> Это движок чиптюна под Sega Genesis. Распакуй, запусти
> `python3 bridge/bootstrap.py`, прочитай `START_HERE.md`, сочини трек в
> его трекерной нотации и отрендери в WAV и VGM.

Почему это работает без деплоя:

- **Архив самодостаточен.** Ядра чипов — это C-исходники, которые
  `bootstrap.py` компилирует на месте за пару секунд (в песочницах с
  интерпретатором кода компилятор есть).
- **Есть дно.** Нет компилятора — работают pure-Python ядра. Нет numpy и
  scipy — работает stdlib. Проверено в комбинации «ничего из этого нет»:
  трек всё равно рендерится, просто медленнее.
- **Никакой сети.** Ни на одном шаге.
- **`START_HERE.md` написан для модели**, а не для человека: вся нотация,
  весь банк инструментов и отдельный раздел «что тебя укусит» (у PSG
  громкость наоборот, DAC отбирает шестой канал, `...` — это «держать», а
  не «пауза») на одной странице.
- **`bridge/manifest.json`** — тот же словарь машиночитаемо, генерируется
  из кода (`python3 python/chipgen.py --info`), так что разойтись с
  реальностью не может; тест это стережёт.

Смысл в том, что путь-плагин и путь-ZIP — это один движок с двух сторон,
а не два проекта.

## Точка подключения нейросети

Контракт не изменился: модель возвращает `List[Event]`.

```python
class Generator(ABC):
    def generate(self, style, bars, bpm, ticks_per_second=192.0, **kw) -> List[Event]: ...
```

```python
from generators import get_generator, available
print(available())   # ['cloud:anthropic', 'local:model', 'local:rule_based']
```

- `local:rule_based` — детерминированная заглушка, ни сети, ни модели, полезна как smoke-test
- `cloud:anthropic` — синхронный вызов облачного API (`cloud_generator.py`)
- `local:model` — честно НЕ заряжен: бросает понятную ошибку вместо того чтобы притворяться рабочим. Это розетка под настоящую локальную сеть, а не готовое решение

Новый бэкенд — это `register("cloud:openai", MyGenerator)`; ни
`sequencer.py`, ни вызывающий код трогать не надо.

Промпт для облачной модели **генерируется из кода** —
`events.describe_vocabulary()` + `instruments.describe()` +
`samples.names()`. Раньше это был строковый литерал, и добавление
инструмента молча оставляло модель в неведении о нём. Теперь разойтись
не может, и на это есть тест. По умолчанию у модели просят трекерный
текст, а не JSON: четыре такта — это несколько сотен байт вместо
нескольких тысяч, и модель видит ритм, который пишет, вместо того чтобы
считать скобки.

Разбор ответа щадящий: канал вне диапазона, нота строчными буквами,
забытый `End`, лишнее поле — чинится и попадает в `warnings`, а не
роняет всю выдачу. Модель, попавшая в 95%, должна быть услышана.

## Что было починено

Шесть ошибок, ни одна из которых не проявлялась как «не работает» —
только как «звучит не так». Первые три — в эмуляции чипов, вторые три —
в тракте между чипами и WAV.

**1. FM был практически не слышен.** `opn2_render()` читал `mol`/`mor`
один раз на выходной сэмпл. Но это не «выход чипа» — это
времяразделённая шина: настоящий YM2612 гонит через один ЦАП все шесть
каналов по очереди, полный проход — 24 внутренних такта. Чтение раз в 24
такта давало один канал, да и то в трёх случаях из четырёх — уровень
резисторной лесенки вместо звука. Выходной сэмпл — это **сумма всех 24
подтактов**, как и делает родной `OPN2_Generate()` в Nuked-OPN2. До
починки FM отдавал ±3 из ±256; вся слышимая громкость демо шла от PSG.

**2. Всё играло октавой ниже написанного.** В `freq_to_fnum_block()` было
`2^(20-block)` вместо `2^(21-block)`. Формула из даташита —
`F-Number = (144 · f · 2^20 / clock) / 2^(block−1)`, что сворачивается в
`144 · f · 2^(21−block) / clock`. Ошибка на единицу в показателе даёт не
фальшь, а идеально чистое исполнение на октаву в стороне — ровно тот
случай, который переживает любое прослушивание. Проверка: A4 = 440 Гц
обязана попасть в fnum 1082, block 4 — значение из всех опубликованных
нотных таблиц Genesis. Теперь попадает, и это тест.

**3. PSG был на 7 центов ниже строя.** Счётчик в `psg.c` проверял ноль и
уменьшался только в ветке `else`, тратя лишний такт на полупериод: канал
играл `clock/(32·(N+1))` вместо `clock/(32·N)`, который предполагает
`freq_to_tone_n()`. Отклонение одинаковое по всему диапазону, поэтому
читалось как «PSG слегка не строит с FM». Сейчас — 0.11 цента от цели.

Плюс сопутствующее: записи в регистры больше не выбрасывают звук.
Записи обязаны тактировать чип, иначе защёлка перезаписывается и запись
теряется; раньше эти такты просто отбрасывались, и смена патча (30
записей ≈ 100 сэмплов) пробивала дырку в звуке. Теперь они копятся в
FIFO, который `opn2_render()` отдаёт первым.

**4. Хэты были не шумом, а периодической волной.** Запись в регистр шума
PSG сбрасывает LFSR в 0x8000 — это настоящее железо и это правильно.
Неправильно делать это на каждом ударе: `noise_on()` переписывал регистр
всякий раз, поэтому хэт, гейтящийся шестнадцать раз за такт, каждый раз
проигрывал одни и те же первые сотни состояний сдвигового регистра.
Измерение: удар №5 коррелировал с ударом №1 ровно на +1.000 — побитово
тот же сэмпл. Это перестаёт быть тарелкой и становится звоном на частоте
шага, и это был самый громкий источник грязи в плотном паттерне.
Настоящие драйверы Genesis выставляют режим шума один раз и дальше гейтят
громкостью — теперь так же. Регистр пишется только при смене режима;
`PSGNoiseOn(restart=True)` возвращает старое поведение, когда сброс нужен
осознанно.

**5. Ресемплинг без антиалиасинга на пути без scipy.** Оба чипа работают
сильно выше выходной частоты (PSG — 223 кГц, это децимация 5:1) и выдают
меандры, гармоники которых уходят далеко за Найквист. Замер на C6:

| путь | мусор/сигнал |
|---|---|
| scipy, FFT-ресемпл | −74.7 дБ |
| numpy, полифазный windowed-sinc | −61.9 дБ |
| голый Python, каскад из трёх скользящих средних | −39.1 дБ |
| **было: box + линейная интерполяция** | **−18.6 дБ** |

−18.6 дБ — это слышимая металлическая грязь под музыкой, которую никакой
подбор инструментов не уберёт, потому что её источник вообще не в
инструментах. Отдельно стоит отметить деталь, на которой легко
провалиться: без дробной задержки (банк фазовых ядер) качество упирается
в −33 дБ, сколько ядро ни удлиняй — джиттер выборки становится
собственным шумовым полом.

**6. Микс не был сведён между чипами.** FM отмасштабирован так, что шесть
каналов на максимуме заполняют int16 — то есть один канал даёт 0.164 от
полной шкалы. `psg.c` делит свой четырёхканальный микс на четыре и
масштабирует в полный int16 — один голос PSG даёт 0.25, почти на 4 дБ
громче полного FM-канала. Эти два масштабирования выбирались независимо и
никогда не сводились друг с другом. В результате один квадрат и хэт
держали тот же RMS, что пять FM-каналов, и хоронили их. Сейчас
`psg_gain = 0.65` ставит один голос PSG вровень с одним FM-каналом на
максимуме — это инженерное решение, а не замер с железа: Mega Drive мешает
чипы в аналоге, и соотношение зависит от ревизии платы. Плюс включён
`dc_block`: лесенка ЦАПа уводила микс на −0.027 (4.3% от пика), это
съеденный запас и щелчок на старте и в конце. Убирается только член на 0 Гц,
так что сама грязь лесенки (сигналозависимый меандр, а не константа)
остаётся на месте.

## Что добавилось

- **VGM-экспорт** (+ обратное воспроизведение), DAC пишется через
  PCM-блок и однобайтовые команды 0x8n, как в настоящих рипах
- **Трекерная нотация** в обе стороны, с фиксированной точкой на
  повторном дампе
- **DAC/PCM на 6-м канале** — закрыт первый пункт из старого «чего пока
  нет». Кит синтезируется кодом: ноль лицензий, ноль мегабайт
- **Пан, LFO, громкость канала, питч в центах, смена темпа** — закрыты
  ещё два пункта оттуда же
- **Ревизия чипа**: `ym2612` (дискретный, Model 1 — с лесенкой ЦАПа,
  грязноватый, пан подтекает) или `ym3438` (поздний ASIC — чистое
  мьютирование). Обе — настоящее железо, выбор за автором
- **10 новых инструментов** (было 4, стало 14) + сериализация патчей
- **Банк выровнен по громкости**: было 12.5 дБ разброса от `orch_hit` до
  `distorted_lead`, стало 1.2 дБ. Патч несёт отдельный `trim` в шагах
  Total Level, который чиповый слой добавляет только к несущим — это
  двигает уровень, не трогая тембр. Числа не подбираются на слух, а
  меряются: `python3 python/calibrate_bank.py --write` рендерит каждый
  патч, берёт максимум RMS по скользящему окну 300 мс (обычный RMS
  несправедлив к перкуссии — короткий удар усредняется с тишиной) и
  решает уравнение относительно медианы банка. Побочный вывод, который
  стоит знать: патч надо проектировать чуть **громче** нужного и глушить
  триммом, потому что поднять его тримм может только до Total Level 0 —
  `orch_hit` в это упёрся, и чинить пришлось сам патч
- **Импорт инструментов из любого Genesis VGM** (`python/vgm_import.py`).
  VGM — это полный лог регистров, то есть патчи лежат прямо в нём.
  Импортёр проигрывает поток, снимает слепок канала в момент key-on
  (единственный момент, когда патч гарантированно такой, каким его задумал
  драйвер — дальше регистры переписываются под огибающие и эффекты),
  схлопывает одинаковые, ранжирует по числу использований и выравнивает
  громкость под встроенный банк. Проверено на круговом прогоне: пять
  патчей вышли обратно побайтово

```bash
python3 python/vgm_import.py song.vgm -o bank.json --audition out/
python3 python/chipgen.py score.trk --bank bank.json -o out.wav
```
- **numpy и scipy стали опциональными**; WAV пишется через stdlib
- **pure-Python ядра** обоих чипов
- **60 тестов**, запускаемых `python3 tests/run_tests.py` без установки
  чего-либо (pytest тоже работает, если он есть)

## Ловушка с порядком операторов

Смещения регистров YM2612 идут как op1, op3, op2, op4 — чип
чередует операторы по 24-слотовому конвейеру, и карта регистров следует
конвейеру, а не блок-схеме. `FMInstrument.operators` хранится в этом же
порядке. Все схемы алгоритмов в интернете и все прочие трекеры нумеруют
операторы op1..op4.

Поэтому новые патчи собираются через `instruments.patch(...)`, который
принимает op1..op4 в обычной нумерации и переставляет сам. Четыре
исходных голоса намеренно оставлены в сыром порядке: они настраивались
на слух именно под эти записи в регистры.

## Технические заметки о точности

- **YM2612**: ядро — [Nuked-OPN2](https://github.com/nukeykt/Nuked-OPN2)
  (nukeykt), реверс-инжиниринг по фото кристалла YM3438, cycle-accurate.
- **Нативная частота YM2612** ≈ 53267.04 Гц (NTSC), выведена из
  отношения «1 вызов Clock = 6 тактов чипа» и 24-слотового FM-конвейера
  (6 каналов × 4 оператора). Рендерится на ней, затем ресемплится в 44100.
- **SN76489**: написан с нуля по спецификации SMS Power! — 16-битный
  LFSR (не 15-битный, как в оригинальном TI-чипе — Sega-версия шире),
  фидбэк на битах 0 и 3 для white noise, сброс на 0x8000, полная
  register-level модель счётчиков. Нативная частота ≈ 223721.56 Гц
  (clock/16).
- Обе частоты — реальные для NTSC Genesis. PAL тоже есть
  (`Sequencer(pal=True)`).
- **VGM** пишется по спецификации 1.71; в заголовок кладётся именно
  Sega-вариант PSG (16 бит, фидбэк 0x0009) — с TI-значениями любой плеер
  отрендерит канал шума неправильно.

## Про pure-Python ядра — честно

`python/fallback/` существует ровно затем, чтобы движок звучал в
песочнице, где есть Python и больше ничего. Это дно, а не смысл проекта.

- **PSG честный.** Те же регистры, тот же 16-битный LFSR, те же отводы,
  та же таблица громкости. Он интегрирует переключения счётчика вместо
  того чтобы шагать по 223 тысячам тактов в секунду на Python — быстрее
  и заодно с антиалиасингом, но модель под интегралом та же самая. RMS
  совпадает с C-ядром.
- **FM — приближение, и говорит об этом вслух.** Берёт у чипа настоящие:
  ROM-таблицы log-sin и exp (сгенерированы формулами и сверены с
  `ym3438.c` побайтово), приращения фазы, таблицу детюна, вывод
  key-code, скорости огибающей, таблицу маршрутизации алгоритмов с
  конвейерными задержками, аккумулятор канала с клиппингом в 9 бит. Не
  берёт: cycle accuracy, LFO, SSG-EG, лесенку ЦАПа. По уровню
  расходится с родным ядром на 0.4–1.7 дБ на большинстве патчей.

Нужен звук чипа — поставь компилятор.

## Диагностика собственного трека (sanity.py)

Движок безропотно исполнит что угодно — включая канал шума, оставленный
включённым на все 60 секунд. Именно так и получился первый трек, который
GPT сгенерировал через мост: он звучал «шумно», хотя ни клиппинга, ни
просадки уровня, ни бага рендера не было — реплей записанного `.vgm`
через наш (уже починенный) движок дал ту же плотность спектра, что и
исходный WAV, побайтово. Разбор регистров показал причину: PSG-канал
шума был включён один раз и ни разу не выключен за весь трек (0
отключений), 8-битный DAC (6-й FM-канал) включился на 2.7с и не
выключался больше 57 секунд подряд (691 096 записей, разрывов длиннее
5мс — 0.047%), панорама нигде не использовалась (везде центр, отсюда
L≡R побитово). Три честных, слышимых решения композитора, не баг движка.

`python3 python/chipgen.py --info` этого не покажет — там движок
рассказывает о себе, а не о том, что написали. Поэтому `compose()` перед
рендером сам прогоняет список событий через `sanity.py`: сколько времени
каждый FM/PSG-канал реально звучит без пауз, сколько раз он ретриггерился
(педаль, перевзятая каждый такт, — это нормально; тот же дьюти-сайкл, но
без единого ретриггера за 60 секунд, — уже дрон), сколько времени DAC
провёл включённым, использовалась ли панорама вообще. Предупреждения
идут в тот же `Result.warnings`, что и ремонт кривого JSON — печатаются
CLI, видны через API. На треках короче 5 секунд процентные пороги ничего
не значат (двухтактный демо-пример с 220-мс kick на быстром темпе
физически не успевает отпустить DAC между ударами — это нормальная
плотная партия, а не стена шума), поэтому там проверка молчит.

## Импорт инструментов: VGM, Furnace, DefleMask

Собственный банк — 19 патчей, сделанных руками. Этого мало для чего-то
кроме демо, и «мало инструментов» было постоянной претензией. Теперь есть
два импортёра, и оба выравнивают громкость под встроенный банк, так что
чужие патчи встают в микс без пересведения:

```bash
# любой Genesis VGM — патчи лежат прямо в логе регистров
python3 python/vgm_import.py song.vgm -o bank.json

# файлы инструментов Furnace / DefleMask / TFM (.dmp .tfi .vgi)
python3 python/furnace_import.py .../instruments/OPN --filter bass -o bank.json

python3 python/chipgen.py score.trk --bank bank.json -o out.wav
```

Furnace поставляется с библиотекой около 600 инструментов YM2612,
разложенных по категориям (bass, guitar, keys, strings, horn, synth,
percussion, drums, wind, effect). Прогнал импортёр по ней целиком: **405
из 406 читаемых файлов**, единственный отказ — реально беззвучный патч,
отклонён правильно.

Две вещи, на которых легко ошибиться, и обе взяты из исходников Furnace
(`fileOpsIns.cpp`, `platform/fmsharedbase.h`, `platform/genesis.cpp`), а
не угаданы:

- **Порядок операторов.** Смещения регистров YM2612 идут op1, op3, op2,
  op4, и массив `op[]` у Furnace хранится в этом же регистровом порядке
  (их `orderedOps = {0,2,1,3}` отображает UI-нумерацию на тот же массив).
  Наш `FMInstrument.operators` — тоже. Операторы копируются позиционно
  без перетасовки, но только потому, что обе стороны используют
  регистровый порядок, а не потому, что порядок неважен.
- **Детюн — не регистровое значение.** Furnace хранит его в своём
  пространстве 0-7 с центром в 3 и переводит таблицей
  `dtTable = {7,6,5,0,1,2,3,4}` при записи в чип. И `.tfi`, и `.dmp`
  хранят значение в системе Furnace. Пропустить перевод — значит тихо
  расстроить каждый импортированный патч: слышно как биения внутри
  патча, а не как что-то похожее на баг.

Проверка корректности — по распределению негармоничности. Если бы
конверсия была сломана, промахи размазались бы ровно по всем категориям.
Вместо этого они идеально повторяют музыкальные ожидания: **drums 82%**,
**effect 65%** негармоничны (так и должно быть у FM-перкуссии), а
**keys 6%**, **horn 17%**, **strings 18%** — в строю. И решающий тест: из
всех патчей, где `multiple=1` у всех четырёх операторов (такие обязаны
попадать точно в основной тон), промахнулся один из 405, и тот при
разборе оказался исправным — артефакт метода измерения.

`.fui` (собственный формат Furnace) намеренно **не** читается: это
версионированный контейнер опциональных блоков, а патчи из `.fui` в
библиотеке дублируются в `.dmp`/`.tfi`. Прочитать треть формата плохо
хуже, чем не читать его вовсе.

## profile.py — то, что `sanity.py` в принципе не может увидеть

`sanity.py` смотрит на список событий целиком и не более того — «канал
занят 87% всего трека» ничего не говорит про то, тихо ли звучит именно
брейкдаун. Канал с арпеджио в других секциях легко набирает больше
`RETRIGGER_CEILING` ретриггеров за весь трек, даже если в ОДНОЙ
конкретной секции повисла незапланированная нота — ветка генератора
паттернов вернула `...` (держать) вместо `===` (выключить), и нота из
дропа звучит все шесть тактов брейкдауна. Агрегат по всему треку это не
видит в принципе — это ограничение самого метода, не баг реализации.

`profile.py` — это дополнительная проверка **по звуку**, не по событиям:
RMS/пик отдельно по каждой секции. Секции — либо через новую директиву
`mark <label>` (одна строка на секцию, `chipgen.py --profile` печатает
по имени), либо по фиксированным тактам, если `mark` не использовался.
Реконструкция реальной находки (ниже) показывает разницу:

| | брейкдаун с багом | брейкдаун без бага |
|---|---|---|
| RMS | 0.0222 (52% от дропа) | 0.0019 (4% от дропа, реальная тишина) |

```
python3 python/chipgen.py song.trk -o song.wav --profile
```

Появилось это не абстрактно: два независимых агента, тестировавших мост,
независимо написали одноразовый numpy-скрипт с RMS по тактам, чтобы
поймать ровно такой баг — один явно зафиксировал в логе сессии, что
«такого инструмента в репозитории нет». Теперь есть, и он использует уже
существующий `Marker` из словаря событий, который раньше ничего не делал.

## Известное свойство: LFO дрейфует между прямым рендером и повтором из VGM

Пока разбирал живой трек с LFO на максимальной ставке (freq=7), нашёл,
что реплей `.vgm` расходится с прямым рендером всё сильнее по ходу ноты,
скачком в конце. Причина понятна и это не баг в обычном смысле: VGM
хранит паузы в сэмплах 44100 Гц (это требование самого формата), а
внутренние тики движка — в несоизмеримой с ней частоте (~53267 Гц у
чипа). Круговая конвертация точно сохраняет суммарную длительность, но
не поточечное число нативных сэмплов между конкретными событиями — а LFO
тактируется именно нативными сэмплами чипа, не «мировым временем», так
что после первого же округления не в ту сторону фаза сдвигается
навсегда и не возвращается. На медленных ставках LFO это практически не
слышно; на самой быстрой — измеримо и, вероятно, на грани слышимости.

Практическое следствие: сравнение «реплей VGM совпадает с оригинальным
WAV» (которым в этом проекте не раз проверяли подлинность чужого
рендера) имеет свой шумовой пол, когда в треке активен быстрый LFO — не
путать это с признаком подделки. Зафиксировано тестом
(`test_fast_lfo_drifts_between_direct_render_and_vgm_replay`), чтобы
поведение было документированным, а не сюрпризом при следующей проверке.

## Чего по-прежнему нет

- SSG-EG не выведен в высокоуровневый API (регистры доступны через
  `ym.write()` напрямую)
- PSG DC-offset трюк для сэмплов не обёрнут отдельным методом
- Обученного чекпоинта под словарь событий в проекте нет — `local:model`
  честно пустая розетка
- Нет живой пошаговой генерации: архитектура batch — сначала весь список
  событий, потом рендер. Для облачной модели, которая выдаёт паттерн
  разом, это ровно то, что нужно; для нота-за-нотой в реальном времени
  понадобится локальная модель в том же процессе

## examples/claude_composition.py — сочинено вручную, не алгоритмом

Не генератор и не подключение к модели — обычная композиторская работа,
записанная как события напрямую: D minor, i-VI-III-VII (Dm-Bb-F-C),
бас/аккорды/лид с реальным мелодическим контуром и паузами для
фразировки, PSG-арпеджио меняется вместе с гармонией.

```bash
python3 examples/claude_composition.py
# -> output/claude_composition.wav + .vgm
```
